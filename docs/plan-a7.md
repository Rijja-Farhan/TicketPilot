# Plan: A7, Ambient agent capstone (TicketPilot v4)

Source: syllabus A7 (Week 4, 12% weight). Rubric focus: D1 framing, D3 architecture, D5 guardrails and security, D8 ML reasoning, D4 verification. Live session L3 is a capstone demo and viva, so every part has to be explainable.

## Context
Make TicketPilot react to a stream of incoming tickets with no prompt. It triages and drafts, routes risky actions to a human, serves the classifier as a tool, and adds a volume anomaly detector. The stream must contain **duplicates, a burst, and prompt-injection tickets**.

Reused from A1 to A6: classifier with the 0.7 threshold, the `classify_ticket` tool, the coworker (for tickets that need real investigation), `verify.py`, the budget, `runstate` durability, the trace, the A6 harness.

## 0. Spec first
`docs/spec-a7.md` holds the event schema, the action-tier table, acceptance criteria and the stream gold file. The gold is written before the first run, with the A6 rules: a gold answer changes only if it was wrong, and each change is logged. Detector thresholds are chosen on a separate calibration stream, never on the evaluation stream.

## 1. The stream (`tools/gen/make_stream.py`, seeded, fixed once)
`data/stream/{calibration,eval}.jsonl` plus gold files. Synthetic only. About 300 events over a simulated 6 hours:
- Normal traffic from classifier val (calibration) and test (eval) texts.
- Duplicates (about 25): exact webhook replays, near-duplicates (same customer, new ID, minutes later), and a legitimate repeat well outside the window that must NOT be dropped.
- Burst: about 40 tickets in 15 minutes on one theme (app down, card payments failing), plus a smaller benign bump as the false-alert decoy.
- Injection (about 15), each labelled with what it tries to do: direct override, hidden in the subject, fake system markup, refund or freeze requests, prompt leak, data exfiltration, tool smuggling, zero-width and paraphrase evasions, another language.
- A single-customer flood (rate cap) and one unknown customer.

## 2. Architecture
```
webhook POST /events -+
scheduled tick -------+-> durable queue (SQLite) -> worker -> triage pipeline -> policy layer -+-> auto actions (low risk)
file replay (tests) --+     dedupe, back-pressure                                            +-> approval queue -> human
                                                          \-> audit log (every step)             approve / edit / reject
```
Package `ticketpilot/ambient/`: events, store, queue, dedupe, guard, policy, audit, triage, anomaly, approvals, cost, webhook, replay, CLI.

## 3. Triggers and approval design
- Triggers: webhook, a scheduled tick that runs the detector, file replay for tests and demos.
- Durable queue: SQLite, `pending -> processing -> done | failed | dead`; a row left `processing` is re-claimed after a lease timeout.
- De-duplication: `event_id` seen -> link; otherwise same customer and near-identical text inside a window -> link `duplicate_of`. Never delete; audit.
- Back-pressure: bounded depth, per-customer rate cap, shed low priority first; fraud is never shed; every shed is audited.
- Approvals: approve, edit (re-validated) or reject (reason); timeouts escalate; notification goes to the owner for the category (logged stub).

## 4. ML as tools
Per event: dedupe -> input guard -> `classify_ticket` -> route. Confident (>= 0.7): accepted, no LLM call. Deferred: the LLM classifies. Flagged tickets never reach the LLM. Then enrich (customer), set priority, draft only where the policy tier allows, escalate risky tickets.

Anomaly detector: counts per 5-minute bucket (deduplicated tickets), rolling mean and std over previous buckets (current excluded), Poisson-aware std floor, alert when z >= k and a minimum count is met, with a cooldown. The explanation is generated by code (category, observed vs expected, z, start, sample IDs). k, window and minimum count are chosen on the calibration stream. Report: burst detected, delay, false alerts on the eval stream, what the decoy did.

## 5. Human-in-the-loop tiers
| Tier | Actions |
|---|---|
| Auto | set category and priority, link duplicates, quarantine, raise an alert |
| Approval | any customer-facing reply, status changes, anything touching money or account state |
| Denied | refunds, freezes, closures, reading other customers' data, unknown tools and actions (default deny) |

The agent never sends or executes. Approval executes through a separate path that re-checks the policy.

## 6. Guardrails
Input validation and normalisation; injection scan; flagged tickets are processed in quarantine (no LLM, no draft, human notified, never dropped). Structural defence: ticket text is data, minimal tool allowlist, the policy layer decides in code. Output checks on drafts: no promised refund, no claimed action, no foreign IDs, no unknown links, amounts must come from the ticket.

## 7. Audit log
Append-only JSONL with a hash chain; every autonomous action, quarantine, dedupe, shed and human decision; `verify-audit` detects tampering.

## 8. Cost per 1,000 tickets
Count model calls and tokens per path; measure per-path averages live on a small sample (Groq's daily token cap prevents a full live run); extrapolate with the stream's measured path mix; two scenarios (with classifier, LLM-only); sensitivity to the deferred share. State what is measured and what is extrapolated.

## 9. Red-team report
At least 20 attacks plus the stream injections; per attack: what was tried, the layer that stopped it or "got through", evidence in the audit log. Run offline against a model scripted to obey every injection (proves the policy layer holds even when the model is fooled), and live on a small subset. What got through is reported honestly.

## 10. Tests and eval
Unit tests for every component; scripted-obedient-model tests; stream replay graded against gold (`evals/run_a7.py`); kill-and-resume; flood. All offline under `LLM_PROVIDER=fake`.

## 11. Order of work
0 spec, stream and gold; 1 queue, dedupe, back-pressure; 2 audit, policy, guard; 3 triage; 4 detector; 5 approvals, webhook, CLI; 6 eval runner, cost, red team; 7 reports and docs.

## 12. Acceptance criteria
See `docs/spec-a7.md`.

## 13. Risks
Groq daily token cap (small live samples); scope creep (no web UI, broker or real notifications); injection "pass" claims (proof is the code-level policy layer under an obedient model); detector tuned to the stream (calibration split); coworker per event is expensive (use only where evidence is needed, budgeted).

## Out of scope
A8, A9 and later, a web UI, auth, classifier retraining.
