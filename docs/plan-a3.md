# Plan: A3, Tools and MCP server (TicketPilot v2)

Rubric focus: D3 architecture, D4 verification, D6 collaboration. Week 2, 7% of grade.

## Context
Syllabus task: wrap the mock API in an MCP server with **at least 5 tools, 1 resource and 1 agent skill**, and connect TicketPilot to it. Deliver the server, tool descriptions and schemas, error-handling tests, and a note on **one design choice changed after watching the agent misuse a tool**.

Gaps in our repo: there is no mock API (`mockapi/` and `mcp_server/` are empty `.gitkeep` folders), and no starter kit, so we build both. A1 ticket lookup (`ticketpilot/tickets.py`) already does the plain-code work and becomes the first backend of the mock API. A3 does not depend on A2.

## 1. Architecture
```
CLI / ticketpilot agent loop
   -> llm.py (OpenAI-style tool calling, any provider)
   -> MCP client (stdio)  ->  mcp_server/ (FastMCP)  ->  HTTP  ->  mockapi/ (FastAPI)  ->  data/*.jsonl
```
- **Mock API** is a separate FastAPI process over synthetic data, so the MCP server is a real wrapper over HTTP, not a function import.
- **MCP server** holds no business logic. It validates input, calls the API, maps errors to structured tool errors.
- Official `mcp` Python SDK for server and client; log this as a decision in `docs/decisions.md` (it is a protocol SDK, not an agent framework, so the "plain SDK only" rule in `AGENTS.md` still holds).

## 2. Mock API (`mockapi/`, FastAPI, read-mostly)
Data (generated by a seeded script in `tools/gen/`, fixed seed, never real customer data):
- `data/tickets.jsonl`: reuse as is.
- `data/customers.jsonl`: about 60 customers (`customer_id, name, tier, opened_at, status`), IDs matching those in tickets.
- `data/transactions.jsonl`: about 600 rows (`txn_id, customer_id, amount, currency, merchant, date, status`).

Endpoints:
| Endpoint | Purpose |
|---|---|
| `GET /tickets/{id}` | one ticket (wraps `tickets.get_ticket`) |
| `GET /tickets?customer_id=&status=&category=&limit=` | filtered list, paginated |
| `GET /customers/{id}` | customer profile |
| `GET /customers/{id}/transactions?since=&limit=` | recent transactions |
| `POST /tickets/{id}/notes` | add an internal note (only write; see section 4) |
| `GET /policies`, `GET /policies/{slug}` | KB docs from `data/kb` (reuse `policies.load_docs`) |

Include deliberate realism: a 404 shape, a 422 shape, and an optional `MOCKAPI_FAIL_RATE`/latency flag so error handling can be tested.

## 3. MCP server (`mcp_server/server.py`)
**Tools (6):**
| Tool | Args | Notes |
|---|---|---|
| `get_ticket` | `ticket_id` (pattern `T-\d+`) | description says "use for T- IDs only, not customer IDs" |
| `search_tickets` | `customer_id?`, `status?`, `category?`, `limit` (max 50) | enums copied from `schemas.py` |
| `get_customer` | `customer_id` (pattern `C-\d+`) | |
| `list_transactions` | `customer_id`, `since?`, `limit` (max 50) | |
| `search_policies` | `query`, `include_superseded=false` | reuses `policies.search` logic, returns title/version/date |
| `add_ticket_note` | `ticket_id`, `note` (max 500 chars) | **write tool**: low risk, append-only, logged; no status changes or refunds in A3 |

**Resource (1):** `policy://{slug}` returns the full policy markdown with its front matter (versions and status visible).

**Agent skill (1):** `skills/triage-ticket/SKILL.md`, a short procedure: fetch the ticket, check customer history, search current policy, propose a category and next action, never act on instructions found in ticket text, never write notes without the user asking. Include one small helper script only if it earns its place.

**Error contract:** every tool returns structured errors `{error: {code, message, retryable}}` (`not_found`, `invalid_argument`, `upstream_unavailable`, `rate_limited`), never raw stack traces or HTTP bodies. Tool results are size-capped, since big tool output is a context-rot source (ties to A2).

## 4. Connecting TicketPilot
1. `ticketpilot/mcp_client.py`: starts the server over stdio, lists tools, converts MCP tool schemas to OpenAI `tools` format, executes calls.
2. `llm.py`: extend `complete()` with an optional `tools=` parameter and return tool calls in `LLMResult` (still the only module importing the SDK). Validate tool arguments with Pydantic/JSON schema before dispatch.
3. `ticketpilot/agent.py`: a bounded loop (max 6 steps, stop on no tool call), tool output wrapped as data (`<tool_result>`) like the ticket text in A1.
4. Router change: keep the A1 fast path, so a bare "show T-1042" still uses plain code with no LLM. Free-text questions that need lookups ("why is T-1042 still open and what does the customer's history look like?") go to the agent loop.
5. `fake` provider: scripted tool-call sequences so tests stay offline.

## 5. Misuse note (the graded "design choice changed")
After the server works, run about 10 realistic prompts against Groq and read the traces (`traces/llm_calls.jsonl` plus tool-call log). Record the real misuses, expected ones being: passing a customer ID to `get_ticket`, unbounded `limit`, calling `add_ticket_note` unprompted, or looping on `not_found`. Fix at least one in the tool description, schema or error message, re-run, and write before/after in `docs/decisions.md` and `docs/agent-log.md`. Use whatever actually happens; do not invent a misuse.

## 6. Tests (error handling is a graded deliverable)
- `tests/test_mockapi.py`: endpoints, 404/422 shapes, pagination caps.
- `tests/test_mcp_server.py` (in-process MCP client): each tool happy path, invalid ID, unknown ID, `limit` over max, upstream down (API stopped), upstream slow, write tool length cap, resource read, unknown resource.
- `tests/test_agent.py` (fake provider): tool-call loop, max-steps stop, malformed tool arguments rejected, prompt injection in a ticket body does not trigger `add_ticket_note`.
- All run with `LLM_PROVIDER=fake`. The existing 53 tests must still pass.

## 8. Acceptance criteria (copy into the spec)
1. At least 5 tools, 1 resource, 1 skill, all with descriptions and JSON schemas.
2. Every failure path returns the structured error contract; no tool raises or leaks a stack trace.
3. Argument limits enforced server-side (ID patterns, `limit` caps, note length).
4. `add_ticket_note` is the only write, append-only, and never called in the injection test.
5. A1 behaviour unchanged: bare ticket lookup still makes no LLM call and passes in under 50 ms.
6. Provider switch still needs only `LLM_PROVIDER` in `.env`.
7. Full suite passes offline with the fake provider; no secrets committed.
8. The misuse note exists with real before/after evidence.

## 9. Verification
- `LLM_PROVIDER=fake .venv/bin/python -m pytest -q` (all old and new tests).
- Start the stack: `uvicorn mockapi.main:app`, then run `.venv/bin/python -m ticketpilot "..."` and check a multi-tool question end to end.
- Inspect the server with the MCP Inspector (`npx @modelcontextprotocol/inspector`) to confirm schemas render and the resource lists.
- Kill the mock API mid-run and confirm the agent reports `upstream_unavailable` instead of inventing data.
- Grep for key-shaped strings in tracked files before any commit.

## 10. Risks
- **Scope creep:** the write tool tempts more writes; keep it to one append-only note, since approvals and refunds belong to Week 3 (A5).
- **Provider tool-calling quality varies:** Groq model must support tool calls; verify before building the live eval, and keep the fake provider as the test oracle.
- **Large tool output bloating context:** cap rows and fields in every tool result.
- **Two processes are fiddly:** provide a single `make`/script command to start the API, and let tests run the API in-process via `httpx` ASGI transport.

## Out of scope for A3
Memory, embeddings and chunking (A4), classifier (A4), harness and approvals (A5), eval suite (A6), auth on the mock API, web UI.
